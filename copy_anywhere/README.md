# CopyAnywhere, for developers

CopyAnywhere is an Anki addon that fills fields from other fields, other notes, other cards
and files, through *copy definitions*: lists of stages that run in order. This file is about
working on it. How to use it is in [`ADDON_README.md`](ADDON_README.md), which is also the
README that ships inside the `.ankiaddon`; this file does not.

## Setting up

The addon is one directory of this monorepo, and the [repository README](../README.md) says
how the monorepo works. From the repository root:

| command | what it does here |
| --- | --- |
| `python build.py install copy_anywhere` | links `shared/` and junctions the addon into `addons21` as `_1_copy_anywhere`; run it with Anki closed |
| `python build.py link copy_anywhere` | just the `shared/` links |
| `python build.py check` | fails if the addon imports a shared package `build.json` does not list |
| `python build.py dist copy_anywhere` | writes `dist/copy_anywhere-<version>.ankiaddon` |

`build.json` names the shared packages the addon uses and its version. The package leaves out
`test/`, `test_anki/` and this file, and ships `ADDON_README.md` and `docs/` so the user guide's
links and pictures resolve.

## Layout

| path | what is there |
| --- | --- |
| `__init__.py` | the entry point: installs the hooks and migrates the config at startup |
| `configuration.py` | the `Config` wrapper, the process types, and the config migrations (`migrate_config`) |
| `config.json` | the defaults Anki's addon manager starts from |
| `logging_setup.py` | one log file per triggered operation, under `user_files/logs/` |
| `hooks/` | what runs a definition: the browser menus, adding and editing notes, reviews, sync |
| `logic/definition_schema.py` | the format-2 definition types and structural validation |
| `logic/definition_migration.py` | converting format-1 definitions into stages |
| `logic/flow_analysis.py` | scope, type, effect and call-graph analysis; what the editor checks and what `effects` records |
| `logic/copy_fields.py` | the operation: which definitions run for which notes, the undo entry, the sync tail |
| `logic/execution/` | the stage evaluator: `runner.py` runs one definition for one note, `evaluator.py` the structural stages, `actions.py` the leaf stages, `commit.py` what happens to a run's changes |
| `logic/preview.py` | running a definition without writing anything |
| `logic/unsaved_note_search.py` | judging a search against a note the collection does not have yet |
| `logic/*_process.py` | the extra-processing steps: regex, kana and word highlighting, and the rest |
| `ui/` | the definitions list, the definition editor, one editor per stage type, the preview pane |
| `utils/` | media-folder files, moving and merging cards, duplicating notes |
| `shared/` | generated by `build.py link` and gitignored: links into `../anki_shared/` |
| `docs/` | the specification, the examples and the pictures the user guide shows |

## Tests

From the repository root, with the dev dependencies the [repository README](../README.md)
lists installed:

```
python -m pytest copy_anywhere/test copy_anywhere/test_anki
```

`test/` runs against a real collection behind a stubbed main window. `test_anki/` drives a
running Anki, for what only that can show: the hooks attaching, `CollectionOp` going through
the task manager, config read off disk; its `conftest.py` says how. Both are in the root
`pytest.ini`'s `testpaths`, so a plain `python -m pytest` runs them with everything else.

The examples in `docs/examples/` are loaded by `test/test_readme_screenshots.py` the way a
stored config is, so one that would not survive being pasted into the config fails the suite.
The same module checks that every picture `ADDON_README.md` links to exists and every picture
the harness makes is linked to. The pictures themselves are only made on request:

```
COPY_ANYWHERE_SCREENSHOTS=1 python -m pytest -q copy_anywhere/test/test_readme_screenshots.py
```

That rewrites `docs/images/`. Run it after changing an editor the pictures show.

## Roadmap ideas

- Copy a note's anything into card custom data, as a card action of its own rather than
  through code.
- Copy into new notes: create notes of existing note types and fill them.
- Copy into note types: new fields, new templates, and their names.
- Copy from card templates into anything.
- Code templates in the editor for the things people write over and over.
